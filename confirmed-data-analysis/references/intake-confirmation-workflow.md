# 自然语言接入与确认工作流

## 目标

用户可以直接用自然语言描述分析诉求。Skill 负责识别分析类型、抽取字段、发现候选数据字段，并按目标能力 Schema 生成初版确认表。用户确认后，系统才生成可执行的分析契约并开始跑数。

核心状态流转：

`自然语言 → 意图识别 → 字段抽取与数据发现 → 草稿 → 用户确认或修改 → 锁定契约 → 跑数 → 官方值对账 → 解释结果`

交互模式：

- `adaptive`：默认模式，只解释陌生、高风险或阻塞字段。
- `guided`：用户需要科普时，为所有待确认字段提供通俗解释和不知道时的处理方式。
- `compact`：用户明确要求简洁且熟悉口径时，只展示必要定义。

用户说“不懂”“解释一下”“这些怎么填”或反复回答“不知道”时，切换到 `guided`。不得因为用户没有使用统计术语就推断其业务信息不足。

## 两层对象

### 1. Request Draft

使用 `request-draft.schema.json`。草稿允许缺少执行必填字段，因为它的作用是把系统理解完整地展示给用户，而不是授权执行。

草稿必须保存：

- 用户原话
- 首选分析类型及最多三个候选类型
- 目标能力 Schema
- 按目标 Schema 整理的初版字段
- 每个字段的来源、置信度、证据和候选值
- 缺失字段、冲突字段和待确认问题
- `execution_allowed = false`

### 2. Confirmed Analysis Contract

使用 `confirmed-analysis-contract.schema.json`。只有该对象可以授权跑数。

契约必须满足：

- `confirmed_request` 通过对应能力 Schema 的严格校验
- 用户明确确认
- 保存确认时间、确认原文和草稿修改记录
- `locked = true`
- `execution_allowed = true`

确认后如需修改口径，应生成新的契约版本并记录 `supersedes_contract_id`，不得静默覆盖旧契约。

## 解析步骤

### 1. 识别分析能力

从支持的能力中选择首选类型：

- 指标查询与趋势 `metric_trend`
- 维度比较与分布 `dimension_compare`
- 漏斗分析 `funnel`
- 留存与 Cohort `retention`
- 增长拆解 `growth_decomposition`
- 异常诊断与归因 `anomaly_diagnosis`
- 随机实验分析与显著性 `experiment_analysis`
- 实验样本量与功效 `experiment_sample_size`
- 倾向得分匹配 `propensity_score_matching`
- 合成控制 `synthetic_control`

最多保留三个候选类型及选择理由。如果无法可靠区分，设置 `selected_capability = undetermined`，先让用户确认分析类型。

### 2. 抽取自然语言实体

至少识别以下信息：

- 想回答的业务问题
- 指标、公式、聚合方式和去重键
- 时间范围、粒度和时区
- 维度、筛选条件和对比基线
- 数据源或候选数据集
- 分析类型专属字段，例如漏斗步骤、留存事件、增长驱动项
- 官方大盘值、适用范围、单位和容差
- 实验或因果分析的分流/处理机制、estimand、alpha、power、MDE、单双侧和诊断阈值

数字和相对日期可以规范化，但必须保留原文。例如，将“12.5 万”规范化为 `125000`，同时将原文保存在 `original_text`。相对日期应在确认表中同时展示原表达和解析后的绝对日期。

### 3. 发现数据字段

如果用户未给物理字段名，可以读取数据集元数据、列名和少量样本，形成候选映射。字段存在不代表业务语义正确，因此以下语义字段即使高置信度推断也必须展示给用户确认：

- 指标公式和分子分母
- 去重键或分析实体键
- 漏斗步骤顺序与转换窗口
- 留存的首次事件、回访事件和观察窗口
- 增长拆解模型及驱动关系
- 官方值的时间范围和指标口径
- 随机分流单位、实验纳入/曝光规则和 estimand
- PSM 的处理前协变量、共同支持和匹配策略
- 合成控制的干预时间、供体池、预拟合窗口和失败阈值

### 4. 生成初版确认表

确认表由 `field_provenance` 渲染。用户熟悉口径时使用紧凑表；出现陌生术语、缺失字段或高风险字段时，使用解释表：

| 字段 | 初版值 | 这是什么意思 | 为什么需要 | 是否阻塞 | 需要确认 |
|---|---|---|---|---|---|
| 分析实体键 | `user_id` | 用来判断两条记录是否属于同一个人 | 避免把一个用户的多次行为重复计算 | 否 | 是 |
| 实验分流单位 | 未确定 | 实验抽签时按什么对象分组 | 检验必须按真正的抽签单位计算误差 | 是 | 是 |

示例仅展示交互格式，不代表任何真实业务数据或默认口径。

表格后只提出阻塞性问题和高风险语义问题，避免逐字段审问。每轮优先询问 1–3 个相互关联的问题。用户可以回复“确认”，用自然语言修改，也可以回答“不知道”。对于“不知道”，按 `user_guidance.unknown_handling` 做数据发现、配置发现、低风险建议或请求指标/实验负责人确认，不得把建议默认值写成用户已确认值。

## 字段来源和确认规则

| 来源 | 含义 | 默认能否自动确认 |
|---|---|---|
| `user_explicit` | 用户本轮明确表达 | 可，但高风险语义仍需整体验收 |
| `dataset_inferred` | 根据数据集元数据或样本推断 | 否 |
| `session_inherited` | 来自本次会话已确认信息 | 可，仍需展示 |
| `memory_hint` | 来自历史记忆或偏好 | 否，永远只作为提示 |
| `product_default` | 产品低风险默认值 | 可，但必须展示 |
| `missing` | 无法获得 | 否 |

字段状态包括 `confirmed`、`inferred`、`defaulted`、`missing` 和 `conflict`。

以下情况阻止生成执行契约：

- 目标能力 Schema 的必填字段缺失
- 同一字段存在未解决冲突
- 必填字段推断置信度低于 0.6
- 指标公式、实体键或时间范围仍含未确认的关键语义
- 多数据源关联键或数据粒度未验证
- 用户提供的官方值与分析范围明显不完整，无法判断可比性

## 用户确认语义

可以视为确认的表达包括“确认”“按这个跑”“没问题，开始”。确认仅针对当前展示的草稿版本。

以下表达不能视为确认：

- 只回答某个澄清问题
- 表示大致认可但仍要求修改
- 系统依据历史偏好推断同意
- 用户沉默或切换话题

确认前不执行 SQL、不下载完整数据、不生成正式分析结论。允许进行只读的元数据发现和小样本预览，以便完成字段映射，但必须清晰标记为“数据发现”，不能冒充正式跑数。

## 跑数后的校验

执行完成后，按 `official-validation-workflow.md` 对用户输入的官方值进行对账。官方值与计算值必须并列展示，官方值不得覆盖计算结果。若差异达到 `warning`、`critical` 或口径不可比，应先输出差异和排查结果，再生成业务解释。

## Skill 编排要求

Skill 的入口逻辑应按以下顺序实现：

1. 保存用户原话。
2. 选择能力 Schema，或在意图不清时请求确认类型。
3. 抽取字段并执行必要的数据发现。
4. 生成 Request Draft 和用户可读确认表。
5. 等待用户确认或修改。
6. 生成并验证 Confirmed Analysis Contract。
7. 仅在 `execution_allowed = true` 时调用分析执行器。
8. 运行官方值对账。
9. 按统一输出契约返回结果。

解析器、确认门和执行器应彼此独立，方便分别测试。自然语言解析结果必须能回溯到原文或数据发现证据。
